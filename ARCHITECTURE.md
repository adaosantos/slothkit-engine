# Architecture

This document records how Slothkit is meant to run in an online game, and why. It's the reference for decisions that span several packages.

Slothkit also works fully client-side for single-player games. Everything below applies to online games, where players must not be able to cheat their inventory, gold, or progress.

## Overview

The server simulates. The browser renders.

```
┌──────────── browser ────────────┐            ┌───────────────── server ─────────────────┐
│                                 │  commands  │                                          │
│  input → send command   ────────┼───────────▶│  command queue → engine (one per player) │
│                                 │            │      │                                   │
│  render ◀── interpolate ◀───────┼────────────┤      ├─ scene deltas + events ──────────▶ │
│                                 │ state, evts│      └─ persistence ──▶ database          │
└─────────────────────────────────┘            └──────────────────────────────────────────┘
```

- Each player has their own engine on the server. Players don't share maps: every hunt is a private instance.
- The browser holds no state of value. It receives scene state and events, interpolates between ticks for smooth rendering, and sends commands (use an item, change the party, travel).
- Seeds and RNG state never leave the server, so drops can't be predicted and nothing can be forged client-side.

## Session lifecycle

| Situation | What happens |
| --- | --- |
| Player connects | Load persistent state, resolve time away (below), regenerate the scene, start ticking |
| Player is connected | Server ticks the engine and streams scene deltas and events |
| Tab hidden | Server keeps simulating but stops streaming until the tab is visible again |
| Player disconnects | Server saves persistent state with the server timestamp and stops the engine |
| Back within the grace period (default 10 min) | Run the missed ticks with `engine.step(n)`. The result is identical to having simulated live |
| Back after the grace period | Estimate progress with the offline estimator, capped at the offline limit |
| Away longer than the offline limit (default 24 h) | The player receives exactly the offline limit's worth of progress, and the hunt ends with the party in town |

Both thresholds are configuration. Hunts can also end earlier for in-game reasons (out of potions, bag full, party wiped), which the offline estimator plays forward using the party's hunting rules.

Time away is always measured with the server clock. The client's clock is never trusted.

## State tiers

| Tier | Examples | Saved? |
| --- | --- | --- |
| **Persistent** | Party units (level, XP, HP, stats), inventory, gold, current map, hunting rules | Yes |
| **Transient** | Positions, wild creatures currently alive, targets, attack cooldowns, effects | No. Regenerated by spawners when a session starts |

Transient state can be thrown away at any time without the player losing anything. That keeps saves small, makes offline estimation work on persistent state only, and lets a returning player see their party hunting on a freshly populated map.

## Persistence

The live engine is the hot state. The database is updated according to what changed:

| Change | When it's written |
| --- | --- |
| Real-money purchases, trades between players | Immediately, in a database transaction outside the engine |
| Rare drops, level ups, valuable item use | Immediately, triggered by engine events |
| Accumulated XP, gold, common loot | Periodic checkpoint (e.g. every 30–60 s) |
| Everything persistent | On disconnect and when a hunt ends |
| Transient state | Never |

Because the simulation is deterministic, a server can also store the last snapshot plus the command log since then, and recover a crashed session exactly by replaying the commands.

## Randomness

- Every random decision uses a named RNG stream (`ctx.rng('loot')`), so systems don't disturb each other's sequences.
- Drops are rolled per kill, with no expected-value shortcuts and no pity timers. A 10% drop over 100 kills can land 5 times or 12 times.
- Offline estimation samples drop counts from the binomial distribution. It's exact (geometric skipping) unless the expected count is very large, where a normal approximation is used only as a performance guard. The player gets the same odds online and offline.
- Offline estimation only runs on the server, so it may use `Math.log` and similar functions. Logic that runs on more than one JavaScript engine must not.

## Responsibilities

**Slothkit provides:** the deterministic engine, game mechanics as systems, save serialization with persistent and transient tiers, the offline estimator, and the server-to-client protocol (scene snapshots, deltas, events) with a lightweight client that interpolates for rendering.

**The game server provides:** authentication, the socket transport, routing each player to the process holding their engine, the database, transactions between players, and deploys that save every running engine before restarting.
